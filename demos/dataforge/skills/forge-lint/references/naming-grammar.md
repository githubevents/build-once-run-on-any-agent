# Naming Grammar Reference

Guide for defining, customizing, and enforcing metric column naming grammars.
All naming rules are driven by the project manifest (`assets/dataforge.manifest.yaml`).

---

## The Grammar Concept

Every metric column name follows a structured grammar -- a pattern that ensures consistency, readability, and machine-parsability across all pipeline files, schema definitions, and downstream consumers.

The grammar is defined by three manifest fields under `naming`:

```yaml
naming:
  metric_pattern: "total_{singular_entity}_{present_verb}_count"
  metric_regex: "^total_[a-z]+(_[a-z]+)*_(create|update|close|...)_count$"
  singularization:
    files: file
    plans: plan
```

---

## Default Grammar

### Pattern

```
total_{singular_entity}_{present_verb}_count
```

### Components

| Component | Rule | Examples |
| :--- | :--- | :--- |
| `total_` | Fixed prefix. Always lowercase. Always present. | `total_` |
| `{singular_entity}` | Singular noun form of the entity. May include multi-word entities separated by underscores. | `ticket`, `change_request`, `sla_file`, `ticket_attachment` |
| `{present_verb}` | Present-tense verb from the approved vocabulary. Never past tense. | `create`, `update`, `close` |
| `_count` | Fixed suffix. Always lowercase. Always present. | `_count` |

### Correct Examples

```
total_ticket_create_count
total_change_request_update_count
total_sla_file_create_count
total_ticket_attachment_update_count
total_incident_close_count
total_release_approve_count
```

### Incorrect Examples

| Wrong | Violation | Correct |
| :--- | :--- | :--- |
| `Total_Change_Request_Create_Count` | PascalCase | `total_change_request_create_count` |
| `total_sla_file_created_count` | Past tense verb | `total_sla_file_create_count` |
| `total_sla_files_create_count` | Plural entity | `total_sla_file_create_count` |
| `sla_file_create_count` | Missing `total_` prefix | `total_sla_file_create_count` |
| `total_sla_file_create` | Missing `_count` suffix | `total_sla_file_create_count` |
| `total_SLA_file_create_count` | Uppercase entity segment | `total_sla_file_create_count` |

## Customizing via Manifest

### Custom Pattern

Override the default pattern in `assets/dataforge.manifest.yaml`:

```yaml
naming:
  metric_pattern: "total_{singular_entity}_{present_verb}_count"
```

Alternative patterns for different use cases:

```yaml
# Event-based metrics (no total_ prefix)
naming:
  metric_pattern: "{singular_entity}_{present_verb}_event_count"

# Duration metrics
naming:
  metric_pattern: "avg_{singular_entity}_{present_verb}_duration_days"

# Boolean flags
naming:
  metric_pattern: "has_{singular_entity}_{present_verb}"

# Percentage metrics
naming:
  metric_pattern: "{singular_entity}_{present_verb}_pct"
```

### Custom Regex

The regex must match every column name that uses the metric pattern. It is used for automated validation.

```yaml
naming:
  metric_regex: >-
    ^total_[a-z]+(_[a-z]+)*_(create|update|close|resolve|delete|complete|assign|approve|reject|send|receive|view|download|upload|sign|convert|sync|import|export|link|open|archive|restore|reopen|submit|issue|void|revise|hold|release|review)_count$
```

This regex is generated by `forge-init` from the verbs it finds in the project's
existing pipeline code, not from the full list above — a project's grammar is
its own house style. Do not edit the resolved manifest to add a verb; it is
regenerated and your edit will be lost. Declare the verb in the seed instead:

```yaml
# dataforge.manifest.yaml
overrides:
  naming:
    verbs: ["publish"]     # unioned with the verbs discovered from code
```

See [Extending the Vocabulary](#extending-the-vocabulary) for the full procedure.

## Singularization Reference

The `naming.singularization` map in the manifest defines how plural entity names convert to their singular form. This table is consulted whenever a metric column is constructed from a table name or entity label.

| Plural | Singular | Resulting Metric |
| :--- | :--- | :--- |
| files | file | `total_sla_file_create_count` |
| plans | plan | `total_change_request_create_count` |
| attachments | attachment | `total_ticket_attachment_create_count` |
| tickets | ticket | `total_ticket_create_count` |
| releases | release | `total_release_create_count` |
| dashboards | dashboard | `total_sla_dashboard_create_count` |
| revisions | revision | `total_article_revision_create_count` |
| elements | element | `total_annotation_element_create_count` |
| items | item | `total_feedback_item_create_count` |
| issues | issue | `total_incident_create_count` |

### Adding Entries

When onboarding a new entity whose source table uses a plural name, add an entry to the manifest:

```yaml
naming:
  singularization:
    invoices: invoice
    responses: response
    comments: comment
    entries: entry
    categories: category
    quantities: quantity
```

The agent uses this map during code generation. If a plural form is not in the map, the agent applies a default rule: strip trailing `s` (or `es` for words ending in `es`). Override the default by adding the explicit entry.

## Verb Vocabulary

The approved verb vocabulary defines all valid action words for metric names. Verbs must always be present tense.

### Standard CRUD Verbs

| Verb | Meaning | Example Metric |
| :--- | :--- | :--- |
| `create` | Entity was created (INSERT) | `total_ticket_create_count` |
| `update` | Entity was modified after creation (UPDATE where updated_at != created_at) | `total_ticket_update_count` |
| `delete` | Entity was removed (soft or hard delete) | `total_document_delete_count` |

### Workflow Verbs

| Verb | Meaning | Example Metric |
| :--- | :--- | :--- |
| `close` | Entity transitioned to a closed/completed terminal state | `total_ticket_close_count` |
| `resolve` | Entity reached a resolved state, whether or not it is also closed | `total_incident_resolve_count` |
| `complete` | Entity was marked as complete (distinct from close when both states exist) | `total_audit_complete_count` |
| `assign` | Entity was assigned to a user or group | `total_task_assign_count` |
| `approve` | Entity was approved in a review workflow | `total_release_approve_count` |
| `reject` | Entity was rejected in a review workflow | `total_release_reject_count` |
| `submit` | Entity was submitted for review | `total_release_submit_count` |
| `issue` | Entity was formally issued to a counterparty (e.g., a credit note) | `total_credit_note_issue_count` |
| `void` | Entity was voided or cancelled | `total_credit_note_void_count` |
| `revise` | Entity was revised (new version created) | `total_article_revise_count` |
| `hold` | Entity was placed on hold | `total_escalation_hold_count` |
| `release` | Entity was released from hold | `total_escalation_release_count` |
| `review` | Entity was reviewed (distinct from approve/reject) | `total_document_review_count` |
| `reopen` | Entity transitioned from closed back to open | `total_ticket_reopen_count` |

### Transfer Verbs

| Verb | Meaning | Example Metric |
| :--- | :--- | :--- |
| `send` | Entity was sent to an external party | `total_notification_send_count` |
| `receive` | Entity was received from an external party | `total_notification_receive_count` |

### Content Verbs

| Verb | Meaning | Example Metric |
| :--- | :--- | :--- |
| `view` | Entity was viewed by a user | `total_report_view_count` |
| `download` | Entity was downloaded | `total_document_download_count` |
| `upload` | Entity was uploaded | `total_screenshot_upload_count` |
| `sign` | Entity was digitally signed | `total_agreement_sign_count` |
| `convert` | Entity was converted from one format to another | `total_quote_convert_count` |

### Integration Verbs

| Verb | Meaning | Example Metric |
| :--- | :--- | :--- |
| `sync` | Entity was synchronized with an external system | `total_crm_integration_sync_count` |
| `import` | Entity was imported from an external source | `total_backlog_import_count` |
| `export` | Entity was exported to an external destination | `total_usage_report_export_count` |
| `link` | Entity was linked to another entity or external record | `total_ticket_link_count` |

### Extending the Vocabulary

A verb that is legal in one project is not automatically legal in another: a
project's `naming.metric_regex` is generated from the verbs `forge-init` found in
its own pipeline code. Adding a verb is therefore a manifest change, not a skill
change.

1. Add the verb to the seed manifest under `overrides.naming.verbs`:

```yaml
# dataforge.manifest.yaml
overrides:
  naming:
    verbs: ["{new_verb}"]
```

2. Re-run `forge-init`. It unions the override with the discovered verb set and
   regenerates `naming.metric_regex`. Never hand-edit the resolved manifest —
   the next run overwrites it.

3. Document the verb meaning in the project's lint references.

4. Ensure the verb is present tense (not `archived` but `archive`, not `restored` but `restore`).

## Validation Rules

### Checking a Column Name Against the Grammar

Given a column name, validate it passes these checks in order:

1. **Prefix check:** Must start with `total_`.
2. **Suffix check:** Must end with `_count`.
3. **Case check:** Must be entirely `lowercase_snake_case` (no uppercase letters, no hyphens, no spaces).
4. **Regex match:** Must match the `naming.metric_regex` from the manifest.
5. **Entity singularity check:** The entity portion must be singular (cross-reference the singularization map).
6. **Verb tense check:** The verb portion must be present tense (check the verb vocabulary).

### Programmatic Validation (Python)

```python
import re

def validate_metric_name(name: str, metric_regex: str) -> tuple[bool, str]:
    if not name.startswith('total_'):
        return False, "Missing 'total_' prefix"
    if not name.endswith('_count'):
        return False, "Missing '_count' suffix"
    if name != name.lower():
        return False, "Contains uppercase characters"
    if not re.match(metric_regex, name):
        return False, f"Does not match pattern: {metric_regex}"
    return True, "Valid"
```

### Programmatic Validation (dbt -- schema test)

```yaml
# schema.yml
models:
  - name: change_request__metrics_snapshot_daily
    columns:
      - name: total_change_request_create_count
        tests:
          - not_null
```

A custom dbt test macro for naming validation:

```sql
{% test metric_name_convention(model, column_name, pattern_regex) %}
    SELECT '{{ column_name }}' AS column_name
    WHERE NOT REGEXP_LIKE('{{ column_name }}', '{{ pattern_regex }}')
{% endtest %}
```

## Custom Grammar Examples

### Event Count Grammar (no total_ prefix)

```yaml
naming:
  metric_pattern: "{singular_entity}_{present_verb}_event_count"
  metric_regex: "^[a-z]+(_[a-z]+)*_(create|update|close)_event_count$"
```

Produces: `ticket_create_event_count`, `task_update_event_count`

### Duration Metric Grammar

```yaml
naming:
  metric_pattern: "avg_{singular_entity}_{present_verb}_duration_days"
  metric_regex: "^avg_[a-z]+(_[a-z]+)*_(create|close|complete|resolve)_duration_days$"
```

Produces: `avg_ticket_close_duration_days`, `avg_task_complete_duration_days`

### Boolean Flag Grammar

```yaml
naming:
  metric_pattern: "has_{singular_entity}_{past_participle}"
  metric_regex: "^has_[a-z]+(_[a-z]+)*_(created|updated|closed|assigned)$"
```

Produces: `has_ticket_created`, `has_task_assigned`

Note: Boolean flags use past participle because they describe a state, not an action.

### Percentage Grammar

```yaml
naming:
  metric_pattern: "{singular_entity}_{present_verb}_pct"
  metric_regex: "^[a-z]+(_[a-z]+)*_(create|close|complete|approve)_pct$"
```

Produces: `ticket_close_pct`, `release_approve_pct`

### Composite Grammar (Multiple Patterns)

Projects may define multiple patterns for different metric types. Use the `metric_patterns` array:

```yaml
naming:
  metric_patterns:
    count:
      pattern: "total_{singular_entity}_{present_verb}_count"
      regex: "^total_[a-z]+(_[a-z]+)*_(create|update)_count$"
    duration:
      pattern: "avg_{singular_entity}_{present_verb}_duration_days"
      regex: "^avg_[a-z]+(_[a-z]+)*_(close|complete)_duration_days$"
    flag:
      pattern: "has_{singular_entity}_{past_participle}"
      regex: "^has_[a-z]+(_[a-z]+)*_(created|updated)$"
```

## System Columns

System columns are the only columns exempt from the metric naming grammar. They use UPPERCASE by convention across all pipeline frameworks.

| Column | Type | Description |
| :--- | :--- | :--- |
| `SNAPSHOT_DATE` | DATE | The partition date for the snapshot |
| `LOAD_TIMESTAMP` | TIMESTAMP | When the data was loaded into the table |
| `SOURCE_ZONE` | STRING | The data zone identifier, from `manifest.platform.zones[].id` (e.g., zone1, zone2) |

These are defined in `manifest.naming.system_columns.uppercase` and must not be renamed, lowercased, or aliased.

### Grain Columns

Grain columns follow `lowercase_snake_case` and are not considered metric columns:

| Column | Type | Description |
| :--- | :--- | :--- |
| `account_id` | BIGINT | Company identifier |
| `workspace_id` | BIGINT | Project identifier |
| `user_id` | BIGINT | User identifier |

Grain columns are defined per grain level in `manifest.grains`.

## CTE Naming

All CTE names must use `snake_case`. This is enforced by `manifest.naming.cte_case`:

```yaml
naming:
  cte_case: snake_case
```

### Valid CTE Names

```
entity_metrics
entity_response_metrics
combined_metrics
all_dimensions
base_dimensions
entity_by_type
entity_pivoted
```

### Invalid CTE Names

| Wrong | Violation | Correct |
| :--- | :--- | :--- |
| `EntityMetrics` | PascalCase | `entity_metrics` |
| `ENTITY_METRICS` | SCREAMING_CASE | `entity_metrics` |
| `Entity_Metrics` | Mixed_Case | `entity_metrics` |
| `entityMetrics` | camelCase | `entity_metrics` |
